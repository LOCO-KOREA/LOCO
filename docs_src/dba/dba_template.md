## 1. 이 문서가 정하는 것

ERD는 **무엇을 저장하나**를 정하고, 이 문서는 **그 저장소를 앱에 어떻게 붙이나**를 정한다.
같은 내용을 두 번 쓰지 않는다. 겹치는 곳은 아래 문서를 가리킨다.

| 질문 | 답이 있는 곳 |
|---|---|
| 어떤 테이블과 컬럼, 제약이 있나 | ERD 5절 (개념·논리), 6절 (내부) |
| 뷰는 무엇을 보여 주나 | ERD 7절 |
| 화면이 부르는 함수는 | API 계약서 4절 |
| 구성요소는 누가 무엇을 맡나 | **이 문서 2절** |
| 어디에 무엇이 저장되고 언제 지우나 | **이 문서 3절** |
| 연결은 누가 열고 스레드는 어떻게 나누나 | **이 문서 4절** |
| 분석 한 번에 DB에 어떤 순서로 쓰나 | **이 문서 5절** |
| 얼마나 빠르고 얼마나 커지나 | **이 문서 6절** |
| 백업, 복구, 업그레이드 | **이 문서 7절** |
| 개인정보 | 이 문서 8절 (분류는 ERD 8절) |
| 웹으로 가면 무엇이 바뀌나 | **이 문서 9절** |

## 2. 구성과 책임

![구성도](DB아키텍처_그림/DBA_1_구성도.png)

| 구성요소 | 맡는 일 | 하지 않는 일 | 코드 |
|---|---|---|---|
| 화면 | 입력을 받고 결과를 보여 준다. 서비스 함수만 부른다 | SQL, 판정·점수 계산 | 화면 도구는 D-API-01 |
| 서비스 | 함수 하나가 트랜잭션 하나. 검증, 수정 이력, 오류 코드 | 화면 그리기, SQL 문장 만들기 | `ergo/service` |
| 저장소 계층 | SQL을 쓰는 **유일한** 곳. 연결, 트랜잭션, 오류 변환 | 업무 판단 | `ergo/db` (연결 규칙은 있고, 저장소 클래스는 이제 만든다) |
| 분석 엔진 | 관절 → 각도 → 자세 판별 → 판정 초안. 순수 함수 | DB와 화면 | `ergo/engine` |
| GPT 어댑터 | `v_gpt_payload`를 읽어 문장을 요청하고 검사한다 | 판정과 점수 | `ergo/gpt` |
| 엑셀 작성기 | 뷰를 읽어 파일을 만든다 | DB 쓰기 (내보내기 기록은 서비스가 남김) | `ergo/report` |
| SQLite 파일 | 조사 데이터 전부 | — | `%LOCALAPPDATA%\ergo-assist\ergo_assist.db` |

**지키는 방향**: 화면 → 서비스 → (엔진 · 저장소 · GPT · 엑셀). 거꾸로 부르지 않는다. 엔진은 저장소를 모르고, 저장소는 엔진을 모른다.

## 4. 연결, 스레드, 트랜잭션

### 4.1 규칙

| # | 규칙 | 이유 |
|---|---|---|
| R1 | 프로그램 하나, 파일 하나. 서버가 없다 | 설치형 PC 프로그램 (NFR-016) |
| R2 | **연결은 스레드마다 하나**. 화면 스레드는 연결 A, 분석 스레드는 연결 B. 연결을 스레드 사이에 넘기지 않는다 | Python `sqlite3`는 연결을 만든 스레드에서만 쓰게 막는다 |
| R3 | 연결을 열 때마다 `foreign_keys = ON`, `busy_timeout = 3000`. 연결은 `ergo.db.open_db`로만 연다. 다른 곳에서 `sqlite3.connect`를 부르지 않는다 | SQLite는 외래키가 기본으로 꺼져 있다. 규칙을 한 곳에 둔다 |
| R4 | 저널 방식은 **WAL**. 읽는 쪽은 쓰는 쪽을 기다리지 않고, 쓰는 쪽도 읽는 쪽을 기다리지 않는다. 쓰기는 한 번에 하나만 가능하다 | 분석 중에도 화면이 읽는다 |
| R5 | 서비스 함수 하나가 **쓰기 트랜잭션 하나**. 중간에 실패하면 전부 되돌린다. 사용자 입력을 기다리는 동안 트랜잭션을 열어 두지 않는다 | 반쪽 저장을 막고 잠금을 오래 잡지 않는다 |
| R6 | **분석하는 동안 DB에 쓰지 않는다**. 시작할 때 한 번 (RUNNING 한 줄), 끝날 때 한 번 (결과 전부)만 쓴다 | 진행률은 저장하지 않는다. 쓰기 잠금이 짧아진다 |
| R7 | 읽기는 뷰로 한다. 엑셀처럼 표를 여러 개 읽는 작업은 **읽기 트랜잭션 하나** 안에서 읽는다 | 읽는 도중 분석이 끝나도 숫자가 서로 어긋나지 않는다 (WAL은 읽기 시작한 시점의 모습을 보여 준다) |
| R8 | SQL은 저장소 계층에만 둔다. 값은 `?`로 넘기고 문자열을 이어 붙여 SQL을 만들지 않는다 | 입력 값이 SQL이 되는 것을 막는다 |
| R9 | 오류를 바꿔서 올린다: 이름 중복 → E-INPUT-003, 그 밖의 제약 위반 (`IntegrityError`) → E-DB-002, 파일을 열 수 없음 → E-DB-001 | 화면은 `sqlite3` 오류를 모른다 |
| R10 | SQLite **{{MIN_SQLITE}} 이상**이 아니면 시작하지 않고 이유를 알린다 | STRICT 테이블 (3.37), JSON 함수 (3.38) |

### 4.2 트랜잭션 단위

| 서비스 함수 | 한 트랜잭션 안에서 하는 일 | 수정 이력 (API 2.1절) |
|---|---|---|
| `create_survey` | `survey` + `survey_reason` | — |
| `save_task_inputs` 등 `save_*` | 입력 저장 → 그 값을 쓰는 호 다시 판정 (`judgment`, `judgment_basis`) → `warning` 갱신 → 이력 | ⑦ ⑧ |
| `confirm_judgment`, `confirm_all` | `judgment` 갱신 + 이력 | ① ② |
| `set_threshold`, `reset_threshold` | `survey_threshold` + 조사의 **모든 단위작업** 다시 판정 + 이력. 중간에 실패하면 각도도 그대로 | ④ ⑤ ⑧ |
| 분석 저장 (분석 스레드) | 5절 | — |
| `delete_survey` | `survey` 한 줄 삭제. 나머지는 CASCADE로 따라 지워진다 | 이력도 함께 지워짐 |
| `export_excel` | 읽기 트랜잭션 → 파일 쓰기 → `export_log` 한 줄 (짧은 쓰기 트랜잭션) | — |

### 4.3 잠금이 길어지지 않게

- 쓰기 트랜잭션 하나는 **{{SAVE_MS}} ms** 안팎이다 (사진 30장 저장, 6절). 사용자가 느끼지 못하는 길이다.
- 그래도 쓰기가 겹쳐 3초를 넘기면 `database is locked`가 난다. 이때의 처리는 미결이다 (DB-05).
- 반드시 피한다: 트랜잭션을 연 채로 사진을 읽거나, 엔진을 돌리거나, GPT를 부르거나, 화면의 입력을 기다리는 것.

### 5.1 결과를 저장하는 순서

외래키 때문에 부모가 먼저 들어가야 한다. 아래 순서는 스키마의 외래키에서 자동으로 확인했다 (순서가 어긋나면 이 문서를 만들지 못한다).

{{SAVE_ORDER}}

### 5.2 현재 분석 바꾸기

- `analysis_run`에는 단위작업마다 `is_current_yn = 1`인 행이 **하나만** 있을 수 있다 (부분 유일 인덱스 `ux_run_current`).
- 같은 트랜잭션 안에서 **이전 분석을 먼저 0으로 내리고, 그다음에 새 분석을 1로 올린다.** 순서가 반대면 유일 인덱스가 막는다.
- `status_cd = 'DONE'`인 행만 현재가 될 수 있다 (CHECK). 취소와 실패는 `is_current_yn`을 건드리지 않는다.

### 5.3 취소, 실패, 갑자기 꺼짐

| 일 | DB에서 | 화면에서 |
|---|---|---|
| 취소 | `analysis_run`을 `CANCELED`로 (`finished_at` 필수). 결과는 쓰지 않는다 | I-ANALYSIS-005 |
| 분석 중 오류 | `FAILED`와 `error_cd` | E-ANALYSIS-001 또는 E-ANALYSIS-009 |
| 프로그램이 분석 중에 꺼짐 | `RUNNING`이 남는다 → **다음에 시작할 때 `FAILED`(error_cd = INTERRUPTED)로 정리한다** (DB-06) | 이전 '현재' 분석이 그대로 보인다 |

### 5.4 다시 계산 (사진을 다시 읽지 않는다)

입력이나 각도 기준이 바뀌면: `still_angle`을 읽고 → 엔진이 자세 비율과 판정을 다시 구하고 → `judgment`, `judgment_basis`, `warning`을 갱신한다. 한 트랜잭션이다 (4.2절). 사진 파일은 열지 않는다 (ERD D-01).

## 6. 성능과 용량 (실측)

측정 환경: {{BENCH_ENV}}. 저널 {{JOURNAL}}, `synchronous = {{SYNC}}`. 데이터는 합성이다: 사진별 값은 무작위 실수 (실제 각도처럼 자리수가 길다), 판정은 단위작업마다 11개, 대표 사진 BLOB은 700바이트로 뒀다. **같은 PC에서도 잴 때마다 두 배쯤 흔들린다** (디스크 동기화, 백신 검사). 숫자는 자릿수로 읽는다.

### 6.1 얼마나 커지나

| 규모 | DB 파일 | 행 수 |
|---|---|---|
| 조사 {{N_SURVEY}}건 × 단위작업 5개 × 사진 30장 | **{{BIG_MB}} MB** | `still_angle` {{N_STILLS}}행, 판정 {{N_JUDG}}행 |
| 분석 1건 | 약 {{KB_PER_RUN}} KB | 사진 30장의 사진 기록 30행 + 사진별 각도 30행 + 판정 11행 |
| 대표 사진 JPEG | 위 합성에서는 700바이트로 뒀다. 실제로 장당 50 KB라면 단위작업 500개에 약 25 MB가 더 든다 (곱셈으로 추정한 값) | |

ERD 6.5절의 분석 1건 크기는 사진 기록과 사진별 각도 행만 잰 값이고, 위 '분석 1건'은 판정·경고·인덱스까지 포함한 값이다.

### 6.2 이 구조를 바꿔야 하는 신호

- 여러 사람이 **같은 파일을 동시에** 쓴다 (공유 폴더에 두는 것도 포함). SQLite는 네트워크 공유 위에서 안전하지 않다 → 9절
- 관절 원자료를 사진마다 저장하기 시작한다 (D-08을 뒤집을 때). 용량이 약 17점 × 3값 × 사진 수만큼 늘어난다
- 조사가 수천 건이 되어 목록 읽기가 눈에 띄게 느려진다. 현재는 {{LIST_MS}} ms이므로 한참 멀다

## 7. 백업, 복구, 업그레이드

### 7.1 백업

- 엑셀을 내보낼 때 `with_db_backup=True`이면 같은 폴더에 `ergo_assist_backup_{YYYYMMDD_HHMM}.db`를 만든다. SQLite 온라인 백업 (`Connection.backup`)이라 **쓰는 도중에도** 일관된 사본이 나온다. 걸린 시간은 6절.
- 앱을 끈 채로 파일을 복사하는 것도 된다. 이때는 `-wal`, `-shm` 파일을 함께 옮긴다.

### 7.2 복구

1. 앱을 닫는다.
2. DB 폴더의 `ergo_assist.db`, `ergo_assist.db-wal`, `ergo_assist.db-shm`을 **모두** 다른 곳에 치워 둔다. (`-wal` 파일이 이전 DB의 것으로 남아 있으면 새로 넣은 파일에 잘못 적용될 수 있다)
3. 백업 파일을 `ergo_assist.db`로 이름을 바꿔 넣는다.
4. 앱을 켠다. 시작할 때 점검 (7.3절)이 돈다.

### 7.3 시작할 때 점검

| 순서 | 점검 | 실패하면 |
|---|---|---|
| 1 | `open_db`: SQLite 버전, `PRAGMA user_version` 확인 | 열지 않는다. E-DB-001 |
| 2 | `RUNNING`으로 남은 분석 정리 (5.3절) | — |
| 3 | 업그레이드가 필요하면 7.4절 | 되돌리고 E-DB-001 |

무결성 검사는 시작 때마다 하지 않는다. 설정의 '점검' 버튼과 백업을 만들 때 돌린다 (6절의 시간).

### 7.4 업그레이드 (스키마 버전)

`schema_version` 테이블의 마지막 번호와 `PRAGMA user_version`을 같게 둔다. 현재는 **{{SCHEMA_VERSION}}**.

1. DB 파일을 `.bak`로 복사한다 (실패하면 중단).
2. 한 트랜잭션 안에서 `migrations/NNN_설명.sql`을 순서대로 실행한다. SQLite는 DDL도 트랜잭션 안에서 되돌릴 수 있다.
3. `schema_version`에 한 줄을 넣고 `PRAGMA user_version`을 같은 번호로 올린다.
4. `PRAGMA foreign_key_check`가 비어 있는지 본다.
5. 하나라도 실패하면 `.bak`을 되돌리고 E-DB-001로 알린다.

주의: 컬럼 삭제나 타입 변경은 `ALTER TABLE`로 못 한다. 새 테이블을 만들어 복사하고 바꾼다. 이런 변경은 시험 데이터로 먼저 돌려 본다.

### 7.5 공간 회수

조사를 지워도 파일 크기는 줄지 않는다. 지운 뒤에 `VACUUM`을 돌린다 (6절). 파일 크기만큼 빈 공간이 필요하고, 도는 동안 다른 쓰기를 막으므로 자동으로 돌리지 않고 설정에서 누르게 한다.

## 8. 보안과 개인정보

- **위치와 권한**: 사용자 폴더 (`%LOCALAPPDATA%`)라서 다른 Windows 계정은 기본 권한으로 읽지 못한다. 설치나 실행에 관리자 권한이 필요 없다.
- **암호화하지 않는다** (DB-07). 이유: 얼굴과 원본 사진은 저장하지 않고, 이름은 별칭으로 써도 되며, GPT 키는 자격 증명 관리자에 따로 있다. 파일 암호화(SQLCipher 등)는 의존성과 키 관리가 늘어난다. 이 판단이 맞는지는 멘토나 보안 요건을 확인한 뒤 확정한다.
- **백업과 엑셀은 앱 밖으로 나간다.** 사용자가 옮기면 앱이 보호할 수 없다. 내보내기 화면에 안내를 넣는다 (화면설계서 S08).
- **GPT로 나가는 것**: `v_gpt_payload`의 {{N_SENT}}개 열만. 나머지는 거르기용이다 (`tests/test_boundaries.py`가 이 구분을 지킨다).
- **SQL 주입**: 4.1절 R8.
- 개인정보 분류는 ERD 8절을 따른다.

## 9. 배포 형태가 바뀌면

배포 형태 (PC 설치 파일 / 웹 주소)는 10/17에 멘토에게 확인한다. 웹이 되면 이 문서에서 **바뀌는 것**은 다음과 같다.

| 무엇이 | PC 설치 (지금) | 웹 (서버) |
|---|---|---|
| DB | SQLite 파일 하나 | 서버 DBMS (예: PostgreSQL). 파일을 복사해 옮기는 방식이 없어진다 |
| 사용자 | 한 명 (Windows 계정) | 여러 명. 로그인이 필요하고, **조사의 소유자와 조직을 구분하는 열이 지금 스키마에 없다** (예: `survey.owner_id`) |
| 동시 쓰기 | 한 번에 하나로 충분 (6절) | 연결 풀, 행 단위 잠금 |
| 원본 사진 | 사용자 폴더에 그대로 (복사 안 함) | **서버로 올라간다.** 얼굴이 있는 사진의 저장·삭제·동의 정책이 새로 필요하다. 개인정보 관점에서 가장 큰 변화다 |
| GPT 키 | 자격 증명 관리자 | 서버의 비밀 관리 |
| 분석 실행 | 사용자 PC의 스레드 | 서버의 작업 큐 |
| 백업 | 파일 복사 | DBMS 백업 |

**그대로 가는 것**: 테이블·컬럼 이름, 코드 값, 관계, 판정 규칙, 서비스 함수 시그니처 (API 계약). 3단계 스키마와 계약을 나눠 둔 덕분이다.

## 10. 데이터 품질과 변경 관리

### 10.1 품질 규칙은 어디에 있나

DDL에서 센 개수: NOT NULL {{C_NOTNULL}}, CHECK {{C_CHECK}}, 외래키 {{C_FK}}, UNIQUE {{C_UNIQUE}}, 트리거 {{N_TRIGGERS}}.

| 품질 차원 | 이 프로젝트에서 | 막거나 확인하는 곳 |
|---|---|---|
| 완전성 | 필수 값이 비지 않는다. 입력이 없으면 '입력 필요' 상태가 된다 | `NOT NULL`, 판정 상태 (기능정의서 3.2절) |
| 유일성 | 같은 호의 판정이 둘이 아니다. 단위작업마다 '현재' 분석은 하나 | `PRIMARY KEY`, `UNIQUE`, 부분 유일 인덱스 |
| 유효성 | 코드 값과 범위가 맞다 (하루 작업시간 0~24 등) | `CHECK` (ERD 4.4절 코드 정의서) |
| 일관성 | 부모 없는 자식이 없다. 확정 ↔ 확정 시각처럼 상태가 맞물린다 | 외래키, 트리거, `CHECK` |
| 정확성 | 법 문구와 기준 값이 원문과 같다. 엔진 계산이 SQL 계산과 같다 | `tests/test_law_text.py` (원문 사본 대조), `v_posture_exposure_check` (엔진 대조), ERD 9절의 제약 시험 30개 |

### 10.2 스키마를 바꾸는 절차

1. 데이터 담당 (한정욱)에게 바꾸는 이유를 말한다.
2. `ergo/db/schema_v1.sql`을 고치고, 이미 쓰는 DB를 위한 `migrations/NNN_*.sql`을 만든다.
3. `python -m unittest discover -s tests -t .` (DB 제약 시험, 계약 ↔ ERD 대조 포함)
4. `python docs_src/build_all.py` (ERD 문서와 그림, API 계약서, 화면설계서, 이 문서가 다시 만들어진다)
5. 필드가 바뀌면 `ergo/contracts.py`와 API 계약서 버전을 올린다.
6. `schema_version`에 한 줄을 넣는다.

문서는 스키마에서 만들어지므로 **문서를 손으로 고치지 않는다.**

## 11. 결정과 미결

| ID | 결정 | 다른 선택지 | 이유 | 상태 |
|---|---|---|---|---|
| DB-01 | SQLite 파일 하나 | 서버 DBMS | 설치형 PC 프로그램, 사용자 한 명, 서버 없음 (9절) | 제안. 10/17 배포 형태 확인 뒤 확정 |
| DB-02 | 저장소 계층은 `sqlite3`와 SQL을 직접 쓴다 | ORM (SQLAlchemy 등) | STRICT·트리거·부분 인덱스를 그대로 쓰고, 규모가 작고, SQL을 직접 익히는 것이 목적 | 제안 |
| DB-03 | 연결은 스레드마다 하나 | 연결 하나를 잠금으로 공유 | `sqlite3` 제약. 읽기를 막지 않는다 | 제안 |
| DB-04 | WAL, `synchronous = FULL` (기본값 그대로) | `NORMAL` | 쓰는 양이 작아 (6절) 느려질 이유가 없고, 전원이 꺼져도 마지막 저장을 잃지 않는다 | 제안 |
| DB-05 | 잠금 시간 초과 때 한 번 다시 시도하고, 그래도 안 되면 E-DB-002 | 새 오류 코드를 만든다 | 오류 코드를 늘릴지는 API 계약서 쪽의 결정 | **미결** |
| DB-06 | 시작할 때 `RUNNING`으로 남은 분석을 `FAILED`로 정리한다 | 그대로 둔다 | 화면에 '분석 중'이 영원히 남는 것을 막는다 | 제안 |
| DB-07 | DB 파일을 암호화하지 않는다 | SQLCipher 등 | 8절 | **미결** (멘토·보안 요건 확인) |
| DB-08 | ERD 4.1절 이름 규칙을 자동으로 검사한다 (시험으로) | 사람이 검토 | 규칙이 있어도 지켜졌는지 보장이 없다 | 제안 (아직 안 만듦) |
| DB-09 | SQLite {{MIN_SQLITE}} 이상을 요구하고 시작할 때 확인한다 | 확인하지 않는다 | 낮은 버전에서는 스키마가 만들어지지 않아 원인을 찾기 어렵다 | 확정 (`open_db`에 있음, 시험 있음) |
