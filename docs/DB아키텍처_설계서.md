# 데이터베이스 아키텍처 설계서

> 문서 ID ERGO-ARCH-001 · 설계 버전 2.0 · 개정일 2026-10-16 · 완성 목표 2026-10-23(Asia/Seoul)

## 1. 구조와 구현 경계

로컬 정리 기준: 실행 진입점은 공통 JSON Lines 서비스 하나다. 낡은 가짜 서비스·별도 샘플 서버·프론트 저장 adapter·DB 계산 뷰 검사기는 제거한다. 기존 1.3 입력의 읽기 변환은 `ergo/legacy/v13.py`에 격리한다. 물리 여섯 테이블과 기존 JSON·분석·출력 snapshot을 변경하거나 일괄 변환하지 않는다. 배포 패키지는 실제 화면·공통 서비스·모델만 포함한다.

Electron renderer → preload → main → Python Application Service → task_input/capture/pose/tags/reba/burden/explanation/report → storage → SQLite다. 기능 모듈은 계산·출력을 담당하고 서비스가 순서를 조정한다. SQLite는 근거·snapshot·결과를 저장하며 계산 규칙을 실행하지 않는다.

상자 들기와 다른 작업에 동일한 일반 작업/가변 사진 경로를 사용한다. 입력 템플릿은 UI 설정이며 서비스·DB에 별도 상자 프로토콜을 추가하지 않는다. 이전 1.3 프로토콜은 호환 읽기 adapter에 한정한다.

여섯 테이블의 기존 컬럼을 유지하고 2.0의 조건 행·분석 범위·모듈 상태·GPT 이력·전후 비교와 조사 맥락·참여·증상 응답은 JSON에 넣는다. 물리 migration은 없다. 세부 매핑은 [ERD](ERD_데이터설계서.md), 서비스 계약은 [API](API_계약서.md)를 따른다.

N02의 DB 위치 표시는 Electron 시작 시 결정한 절대경로를 Python의 `LOCO_DB_PATH`에 그대로 전달해 일치시킨다. 기존 기본 경로·통합 실행의 명시 DB 지정과 여섯 테이블은 유지한다. 연결 확인은 기존 서비스 조회 결과를 사용하고, 복사·폴더 열기는 main이 보관한 경로에만 수행한다. DB 선택·전환·자동 복사·병합은 추가하지 않는다.

## 3. 파일과 런타임

| 자원 | 위치·책임 |
|---|---|
| 앱/서비스 | 설치/배포 디렉터리; Electron·Python과 필요한 패키지 |
| SQLite | 사용자가 선택한 파일; 기본 경로를 실행 안내와 UI에 표시 |
| 원본 사진 | 사용자가 등록한 로컬 경로; 앱은 원본을 변경/삭제하지 않음 |
| 모델 | 배포 시 지정한 TFLite; 버전과 전처리를 snapshot에 기록 |
| Excel | 사용자가 선택한 출력 경로; EXPORT_LOG에 당시 snapshot/receipt |
| API 키 | Python 환경 OPENAI_API_KEY; DB/renderer/패키지에 저장하지 않음 |

requirements-desktop.txt는 Pillow, numpy, openpyxl, ai-edge-litert, opencv-python-headless, OpenAI Python SDK를 선언한다. 목표 런타임은 CPython 3.12 x64다. MoveNet은 공식 버전 URL에서 받아 SHA-256 검증하며 모델 바이너리는 저장소에 넣지 않는다.

DB·모델·사진·출력 경로에 공백/한글이 있어도 인자를 목록으로 전달한다. Python 프로세스는 windowsHide=true로 시작한다. 비밀키를 로그/예외 원문에 출력하지 않는다. 쉬운 설명 생성에는 사진을 보내지 않는다. 별도 사진 관찰은 사용자의 사진 분석 요청에 따라 현재 크롭 이미지를 전송한다.

## 5. 통신과 비동기

main은 Python 프로세스 하나와 UTF-8 JSON Lines로 통신한다. request_id로 응답을 연결하고 stdout은 응답 전용, stderr는 로그다. Python 응답 쓰기를 메시지 단위로 직렬화해 두 스레드의 JSON이 섞이지 않게 한다.

start_analysis는 snapshot·RUNNING 행과 핸들을 먼저 반환하고 분석을 백그라운드에서 수행한다. GPT 요청도 별도 작업으로 처리하되 원래 request_id로 최종 결과를 돌려준다. 파일 선택·설정 조회·입력 저장이 GPT 네트워크 대기 때문에 막히지 않아야 한다. HTTP 서버나 DB를 IPC로 사용하지 않는다.

추론·API 호출·Excel 렌더링 중 DB 트랜잭션을 잡지 않는다. 각 작업 스레드는 자신의 SQLite 연결을 사용하며 쓰기는 서비스의 짧은 잠금/트랜잭션으로 직렬화한다. 완료 시 저장 대상의 존재를 다시 확인한다. 입력 수정 중인 분석은 당시 snapshot으로 끝나며 현재성은 조회에서 계산한다.

요청 범위와 각 모듈 상태를 저장한다. 미요청을 완성으로 표시하지 않고, 0개 사진을 요청한 경우의 실패/미완성도 계약대로 반환한다. 취소는 입력·이전 결과를 보존하고 지연 완료가 취소 상태를 덮어쓰지 않도록 확인한다.

## 6. 주요 저장 흐름

### 입력·사진

서비스가 기존 입력과 새 입력을 비교해 실제 변경 시 revision을 한 번 올리고 검토를 무효화한다. 사진 경로 재연결은 같은 photo_id의 메타만 바꾸고 수동/관찰값을 보존한다. 다른 사진 교체·삭제는 관련 배정·관찰·수동값을 함께 갱신한다. 사진 동의만 바뀌면 계산 revision은 유지한다.

작업자/방법/작업 높이 변경, 촬영조건 변경, 모델/전처리 변경의 수동값 처리 범위는 기능정의서 §6을 따른다. 직접 관찰과 AUTO_ACCEPTED를 구분해 모델 변경이 현장 사실을 지우지 않게 한다.

조사 메타 JSON에는 최초/정기/수시 유형, 수시 사유 유형, 작업장 상황의 설비·작업량·속도·업무형태 변화, 근로자 참여기록, 증상조사 방법·익명 응답·요약을 저장한다. 응답 이름은 선택이며 익명 응답 코드를 기본 사용한다. 과거 행의 빠진 필드는 UNKNOWN/빈 값으로 노출하고 명시 저장 전까지 기존 JSON을 바꾸지 않는다.

### 분석 시작·완료

시작 트랜잭션에서 입력·PHOTO·설정의 snapshot, ANALYSIS 행, TASK.latest_analysis_id를 함께 저장한다. 계산은 snapshot만 읽는다. 완료는 해당 analysis_id의 계산 키·모듈 상태·시각을 갱신한다. 기존 RUNNING 결과를 새 FINISHED 행에 복사하지 않는다.

완료 시 TASK 최신 포인터를 새로 쓰지 않는다. 삭제된 분석은 재생성하지 않는다. FAILED/CANCELED 이후 늦은 성공 응답을 FINISHED로 바꾸지 않는다. 부분 결과는 각 모듈 상태와 함께 저장한다.

### 계산·AI·조사자 결론의 부분 저장

storage는 트랜잭션 안에서 최신 result_json을 읽어 소유한 경로만 바꾼다. 계산은 pose/slot_tags/tags/reba의 계산 부분/judgment의 계산 부분/module_states/관련 notes만, AI 편집은 해당 text_id의 레코드만 바꾼다. 대표 선택·조사자 결론은 계산 부분과 분리한다.

계산을 마친 오래된 객체의 ai를 다시 저장하는 경로를 금지한다. GPT 생성마다 새 text_id의 레코드를 추가하므로 오래된 응답이 기존 편집/적용 레코드를 덮어쓰지 않는다. 생성 완료만으로 활성 적용문을 바꾸지 않는다. 사용자가 text_id를 지정해 적용할 때 같은 목적의 is_active를 원자적으로 전환한다. 과거 적용문과 그 입력 요약은 보존하고 해당 요약으로 설명 현재성을 계산한다.

조사자 결론 저장과 SURVEY.reviewed=false는 한 트랜잭션이다. 대표 사진/설명 편집은 계산 결과에 대한 검토 표시를 그대로 두되 각 편집의 출처·시각을 보존한다.

### 출력·전후 비교

한 읽기 snapshot으로 현존 모든 작업, 작업별 선택 분석, 미분석 작업, 별도 비교 분석, 조사 메타·검토를 묶는다. report.build_overview(snapshot)를 UI·Excel·receipt가 공유한다. 미리보기는 출력 파일·로그를 만들지 않는다.

렌더링은 같은 snapshot으로 한글 시트를 만든다. 공식 서식 구성의 `유해요인조사표`·`부담작업 해당 여부`·`체크리스트`는 조사 유형과 관계없이 항상 만들고, `증상조사표`는 익명 응답이 있을 때만 만든다. 조사 유형·수시 사유·참여·작업장 상황·증상조사 기록은 `유해요인조사표`의 칸에 반영한다. 빈 항목을 완료로 채우지 않고 조사자에게 대조/검토 필요를 표시한다. 파일 쓰기 실패는 EXPORT_ERROR이며 성공 로그를 남기지 않는다. 파일 완료 후 EXPORT_LOG를 저장한다. 파일과 SQLite를 단일 원자 트랜잭션으로 보장하지 않는다. 파일은 생성됐지만 로그 저장이 실패하면 DB_ERROR와 생성 경로를 알려 준다. 이를 정상 출력 완료로 보고하지 않는다.

비교 대상의 두 분석은 같은 조사에 속하는 서로 다른 ID여야 한다. 없는 ID를 최신 분석으로 몰래 대체하지 않는다. 호별 상태를 병기하고 REBA 규칙·프로토콜·대상 수·전체 완성이 맞을 때만 최대 점수 차이를 계산한다.

## 7. 버전 호환과 재현 한계

기존 1.3 입력은 메모리상 편집 DTO로 정규화하고 명시 저장 전에는 DB를 바꾸지 않는다. 편집 DTO의 legacy_input에 이전 TASK.input_json 전체를 보존하고 환산값은 새 직접수치에 null로 두어 재확인한다. 기존 분석·출력 snapshot은 수정하지 않는다. 이전 상자 고정 프로토콜은 과거 읽기에만 남기며 새 관찰 하중·망라성·측면 확인을 추정하지 않는다.

2.0 계산 재현에는 입력·설정·규칙/모델/전처리 버전이 필요하다. 이미 저장한 관절·점수는 읽을 수 있지만 원본 사진/모델 파일을 보관하지 않으면 재추론은 제한된다. GPT는 같은 입력에서도 같은 문장을 보장하지 않으므로 실제 응답·입력 요약을 보존한다. 출력 당시 Excel 값은 ExportSnapshot에서 확인한다.

## 로컬 구현 보완 기록

계산 worker는 계산 필드만 쓰고, AI 생성/편집/적용·조사자 결론·대표 사진은 최신 result_json의 해당 경로만 트랜잭션으로 편집한다. 결론 변경과 검토 해제는 같은 트랜잭션이며 검토 history를 JSON에 보존한다. 출력 snapshot은 하나의 SQLite 읽기 트랜잭션에서 구성한다. 설정과 영향을 받는 2.0 입력 revision 갱신도 같은 쓰기 트랜잭션이다.

Windows 포터블 디렉터리는 Electron·PyInstaller로 묶은 Python 서비스·공식 모델을 포함한다. 빌드 명령은 scripts/build_windows.py이며 설치된 Python/Node를 찾아 실행하지 않는다. DB는 쓰기 가능한 사용자 앱 데이터 경로에 유지한다. 빌드/실행 검증과 외부 검증 경계는 local-verification.md를 따른다.

모듈별 책임과 단방향 의존은 [모듈 지도](module-map.md)를 따른다. 서비스와 저장/보고서는 facade와 entity/domain 모듈로 분리하고 앱별 Runtime에 DB·잠금·취소 상태를 주입한다. 여섯 JSON 테이블과 불변 snapshot 계약은 유지한다. 전체 결과 덮어쓰기와 최신 분석 포인터를 임의로 바꾸는 폐기된 저장 API는 제거했다.

## 적응형 입력 저장 (2026-10-22)

[적응형 계약](adaptive-intake.md)의 선택 JSON `conditions.intake_session`에 사실·질문 문맥·출처·모름 상태를 저장한다. 물리 migration·테이블·trigger는 추가하지 않는다. 실제 계산 입력은 기존 필드로 투영한다. 네트워크 대기 중 잠금을 잡지 않고, 수정 revision이 일치하면 부분 반영하고, 바뀐 경우 늦은 제안을 최신 입력에 재조정한다. 보조 메타데이터 키는 공통 변수 `AUXILIARY_CONDITION_KEYS`에서 관리하고 전후 비교의 조건 변화에서는 제외한다. 과거 snapshot은 재작성하지 않는다.

동일 JSON의 `last_ai`에 마지막 실제 요청의 상태·모델·사유·시각·지연·응답 ID를 보관한다. 키/인증정보는 저장하지 않는다. 정보 추출을 저장한 뒤 질문 계획을 재요청할 때도 네트워크 대기 동안 DB 잠금을 잡지 않는다.

AI 입력 정리·후속 질문·설명 생성은 공통 설정 계약(`ergo/ai_config.py`, API 계약서 §6)을 공유한다. 모델·추론 강도·요청 시간·토큰 한도는 변수이며, 두 설정 화면도 서버 필드 정의로 렌더링한다. APP_SETTINGS의 기존 JSON에 저장하며 테이블·이전 분석 snapshot은 추가/변경하지 않는다.

## 추가 질문 최소화 (2026-10-23)

계산기가 이미 완료한 범위의 작업 특징은 후보와 묶음 서식 모두에서 제외한다. 원래 미확인 값을 NO로 저장하지 않는다. 작업 설명을 먼저 보이는 답변 칸에서 한 번에 정리하고, 개별 수정은 접힌 영역에서 제공한다. 화면에 열거된 남은 작업 특징은 사용자가 명시적으로 한 번 확인하여 NO로 저장할 수 있다. 먼저 작성 중 설명과 직접 선택을 저장하며 새로 알려진 YES, 이전 USER 모름, 이미 확인된 값은 일괄 확인으로 덮지 않는다.

공통 intake POLICY.optional_photo_destinations는 사진 점수를 더 보완할 때의 항목을 정의하고 form_prompt_limit은 한 자연어 안내에 나열할 항목 수를 정의한다. 사진의 미확정 보완 항목만 남으면 기본 팝업을 강제하지 않고, 사용자가 선택해 더 확인할 수 있다. 해당 값은 미확인으로 보존하고 REBA 미완성/현재 정보 출력의 기존 의미를 유지한다. 작업 정보가 충분하거나 사용자가 모른다고 확인한 뒤에는 빈 단계를 건너뛴다. 미전송 설명/직접 수정은 결과 이동 전에 저장한다.

회귀는 test_question_minimization.py와 frontend-question-minimization.cjs에서 계산 완료 시 9개→0개, 남은 특징 한 번 확인, USER 모름/직접 YES 보호, 미전송 설명 우선 처리와 실패 보존을 검사한다. 실제 질문 수는 저장 필드 수 또는 접힌 사진 보완 수와 구분하여 사용자 답변 동작으로 검증한다.

## 사진별 관측값 소유권 (2026-10-23)

사진 자세 값은 같은 원본 사진·신체 부위에만 적용한다. `manual.<scope>.<field>@photo:<photo_id>`가 정식 식별자이며 `photo_id`, 사진 방향, 원래 각도·신뢰도·측정 정책·엔진 근거를 함께 보존한다. 대표가 아닌 사진에서 읽은 값도 저장하지만 대표 사진의 빈 자세를 대신 채우지 않는다. 같은 사진에서 이미 확인한 값과 직접 모름으로 남긴 값은 다시 묻지 않는다. 남은 질문·묶음 서식에는 ‘왼쪽에서 찍은 사진 · 오른팔’처럼 사진 방향과 신체 부위를 표시하고 내부 식별자는 노출하지 않는다.

기존 `@default` 자세 값은 당시 대표 사진에만 연결하는 호환 별칭이다. 이미 저장된 사진별 USER 값·모름을 옛 자동 추정 별칭으로 덮지 않는다. 사진 교체·삭제 시 다른 사진의 사용자 값과 원문·시각을 보존하고 제거된 사진 값은 현재 계산에 투영하지 않는다. 동일 원본·모델 설정·근거를 반복 조회하거나 재시작하면 저장 JSON·revision·근거 시각은 변하지 않는다.

정면·후면의 몸통·목 기울임과 팔 벌림 관측은 원래 사진·신체 좌우별로 보존한다. 한쪽 팔의 최대 각도를 양팔에 복사하지 않으며 확실한 양성 측정만 자동 변환한다. 낮은 신뢰도·점수 경계·손 가림·손바닥 방향 불명확은 확인 대상으로 남긴다. 참고용 목 각도와 추정 3D 좌표는 기존 REBA 확정값으로 승격하지 않는다. 하루 시간·하중 추정, 대표 사진 선택, 양팔 REBA 완성·최댓값 계산은 유지한다.

기존 여섯 테이블과 TaskInput 2.0을 유지한다. `TASK.conditions.intake_session`의 선택 `photo_observations`와 fact 소유권·근거 메타데이터로 저장하며 물리 migration은 없다. 분석·출력 snapshot은 불변이고 Excel 입력 근거는 각 행의 실제 사진 식별자로 조회한다. 같은 범주값인 두 사진도 각자의 각도·인용을 유지한다. 세부 계약과 검증 한계는 [사진별 검증](verification/2026-10-23-photo-ownership.md)을 따른다.

DB 스키마·기존 snapshot·USER 우선권은 바꾸지 않는다.

### 실제 사진의 AI 관찰 (2026-10-23)

사용자가 사진 분석을 요청하는 기존 intake_turn 계획 실행에서 등록된 현재 크롭 사진을 실제 Luna 이미지 입력으로 보낸다. 계약은 `ergo.vision.contract`, 서비스는 `service.photo_vision`이며 모델·추론 설정은 기존 ai_config를 공유한다. 사진별 동작·몸통·목·무릎·좌우 팔·좌우 손목·잡은 모습 9개 관찰과 보이지 않거나 모호한 이유를 보존한다. MediaPipe의 수치 각도와 구분한다. `conditions.intake_session.photo_vision` 및 동일 응답 경로에 사진별 원본/전송 JPEG SHA, task/photo 소유권, signature, raw_response, 연결·진단을 저장하고 base64/EXIF를 DB에 넣지 않는다. 여섯 테이블과 과거 snapshot은 유지한다.

등록 이미지/view/소유권·모델/추론/프롬프트·이미지 정책으로 캐시하며 읽기·재시작·직접 선택 답변·plan=false에는 이미지 API를 호출하지 않는다. 변경된 사진의 최초 요청은 사진별 병렬 실행하며 지연 응답을 시간으로 폐기하지 않는다. 다른 사진이나 삭제·교체된 작업에 이전 결과를 적용하지 않는다. 불확실/안 보임은 NO가 아니다. 허용된 분명한 boolean 자세와 4개 작업 특징의 YES만 별도 검증 경로로 source=VISION에 반영할 수 있다. USER(직접 모름 포함), 텍스트 AI, SAVED, 유효한 POSE를 우선한다. 사진에서 무게·힘·시간·횟수·정밀 각도·법정/의학 판정을 만들지 않는다. 상세는 [photo-vision.md](photo-vision.md)를 따른다.

### 사진 등록 세대와 사용자 사진 상황 우선권 (2026-10-23)

`photo_identity.REGISTRATION_KEY`는 새 PHOTO.metadata_json 행에 UUID를 부여하며 update로 교체하지 않는다. 물리 스키마는 유지한다. legacy 행은 경로/소유 ID로 결정되는 토큰을 읽고 조회 중 metadata를 쓰지 않는다. 사진 signature는 [view,photo_id,원본SHA,등록세대]이며 과거 triple을 호환한다. 같은 SQLite ID·파일경로·바이트·view로 재등록해도 이전 이미지 및 텍스트 사진 응답이 새 등록에 적용되지 않는다.

사용자가 context=NO로 사진 상황을 부정하면 raw 관찰과 캐시는 보존하되 VISION 소유 manual/작업특징 입력은 UNKNOWN으로 돌려 실제 투영값도 해제한다. USER·텍스트 AI·SAVED·POSE 소유 값은 건드리지 않는다. context=YES로 직접 정정하면 같은 이미지 관찰을 재사용하며 추가 이미지 API를 호출하지 않는다. 같은 turn의 텍스트 추출 뒤 저장에도 이 우선권을 적용한다.
