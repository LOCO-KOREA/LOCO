# 적응형 추가 확인 계약 · 2026-10-23

사진·작업 설명 → AI 자동 정리·저장 → 부족한 정보만 대화 팝업에서 확인 → 결과 → 검토·설명 → Excel 순서다. 사용자가 기본 입력 폼을 모두 채우는 흐름이 아니다. AI가 기존 설명·MoveNet 값으로 채울 수 있는 것을 먼저 채우고, 팝업에서 한 번에 한 질문만 한다. 선택지가 있는 질문은 선택 버튼으로 답하고 필요한 경우 ‘직접 설명하기’를 열어 자연어로 보충한다. 숫자·텍스트 질문은 답변창을 기본 제공하며 정리·저장·계산 연결은 앱이 처리한다. 새 운영 승인·배포 차단·AI 성공 필수 절차를 추가하지 않는다.

## 공통 계약과 모듈

`ergo/intake/contract.py`의 `VERSION`, `METHODS`, `POLICY`, 필드 catalogue가 기준이다. 항목·단위·선택지는 기존 질문 정의와 조건 행 매핑에서 조립한다. 프론트는 `intake_contract`를 한 번 조회하고 반환된 메서드 이름·저장 키·필드·정책으로 화면과 요청을 구성한다. 필드 경로나 AI 질문 문구를 프론트에서 새로 판정하지 않는다.

| 모듈 | 책임 |
|---|---|
| `ergo/intake/contract.py` | 공통 변수, 대상 필드, 조건 행 연결, strict 응답 schema |
| `ergo/intake/facts.py` | 값·단위·근거 검증, 사용자 우선 병합, 기존 TaskInput으로 투영 |

| `ergo/gpt/intake.py` | 현재 값·누락 후보·현재 질문을 받아 자연어 추출과 추가 질문 선택 |

| `frontend/intake/activity.js` | 처리 중 애니메이션·실제 경과 초·15초/45초 대기 안내 |

## 서비스 DTO

- `intake_contract {}` → `{version,session_key,methods,policy,states,sources,ai_states,fields}`. 질문 수는 `policy.question_limit=1`, 답변 예시는 필드의 `reply_example`을 사용한다.
- `intake_session {task_id,views?}` → 세션 복원/생성, 사진 측정 저장, 현재 상태. `views`는 방향→같은 작업 사진 ID이며 빈 객체도 가능하다.
- `intake_turn {task_id,text?,answers?,expected_revision?,plan?,focus?,task_created_at?}` → 직접 답변을 우선 저장한다. `plan=true`이고 구조화한 `answers`만 있으며 `text`가 비어 있으면 외부 AI 재호출 없이 저장 후 다음 질문을 로컬 계획한다. 자유문장 추출과 `answers`·`text`가 모두 빈 명시적 재시도는 기존 AI 경로를 유지한다. `plan=false`는 직접 편집 자동 저장 경로다. AI 실패 시에도 직접 답변과 기존 값은 유지한다.

직접 답변은 `{target,condition,value,quote?}`, 현재 질문 문맥은 `{target,condition}`이다. 회차 응답은 `{task,contract,facts,questions,remaining_count,progress,complete,judgments,reba,preview,reason,dropped,diagnostics,history,messages,ai}`다. `ai`는 `{status,model,reasoning_effort,requested_reasoning_effort,reason,observed_at?,elapsed_ms?,response_id?}`이며 NOT_REQUESTED/CONNECTED/ERROR 중 하나다. 실제 응답 결과를 `session.last_ai`에 저장하며 설정·키의 존재만으로 CONNECTED로 기록하지 않는다. 사용자 팝업에서는 모델·추론 강도·연결 성공 상태를 숨기고 처리 중·실패만 일반 안내로 표시한다. `complete=false`여도 현재 정보로 결과를 생성할 수 있다.

질문 항목은 선택적으로 `paired_question`을 포함한다. 서비스는 현재 누락 후보에 같은 manual 항목의 반대쪽(LEFT/RIGHT)이나 반대쪽 사진 방향(`view_LEFT`/`view_RIGHT`)이 있을 때만 기존 질문 DTO 형태의 짝 질문을 붙인다. KNOWN이거나 USER가 UNKNOWN으로 답한 쪽은 다시 묻지 않는다. 이는 서비스가 만든 표시 메타데이터이며 AI가 임의로 짝 질문을 만들지 않는다. 최상위 `questions`는 한 항목을 유지한다. 관련 항목 묶음은 선택적으로 `answer_questions:[AdaptiveIntakeQuestion,...]`와 `group_title:string`을 포함한다. 각 member는 고유 target·condition·identity와 선택지를 유지하며 중첩 pair/group은 포함하지 않는다. `answer_questions`가 있으면 그 목록을 사용하고 root의 짝 질문을 중복 표시하지 않는다.

`progress`는 `{completed_count,total_count,remaining_count,percent,dynamic:true}`다. 현재 작업·조건·사진에 필요한 확인 범위에서 처리한 항목과 남은 질문 후보를 집계하며, 한 번에 보여 주는 `questions` 배열 길이나 저장된 fact 전체 개수로 진행률을 계산하지 않는다. 알려진 값과 사용자가 모름으로 넘긴 항목은 확인 처리로 세지만, 무관한 조건·사진 항목은 제외한다. `total_count=completed_count+remaining_count`, 퍼센트는 처리 비율을 정수 내림하며 대상이 0개이면 100이다. 답변으로 작업 종류·조건이 드러나면 전체 항목과 퍼센트가 바뀔 수 있다. 이 값은 추가 질문 확인 진행이며 계산 완성을 나타내는 `complete`와 별개다. 100%여도 모름·검토 항목은 결과에 남을 수 있다. 진행률은 응답 시 계산하는 메타데이터이며 DB 스키마나 분석 snapshot을 변경하지 않는다.

각 fact는 `{target,condition,value,state,source,quote,updated_at,conflict?,angles?,origin?}`다. 상태는 KNOWN(사용 가능), ESTIMATED(사진에서 읽었으나 낮은 신뢰도/경계), UNKNOWN(모름·재확인), CONFLICT(서로 다른 진술)다. 출처는 USER/AI/MOVENET/SAVED다. 대상 항목의 type과 choices에서 모델 응답의 항목별 schema를 생성해 숫자/선택 값이 섞이지 않게 한다. 낮은 신뢰도 추정은 후보로 저장하고 한 번의 사용 선택으로 반영할 수 있다. 실제 관측값으로 몰래 승격하지 않는다.

AI 응답은 `answers:[{target,condition,number,text,quote}], questions:[{target,condition,text,reason}]`다. 답변 근거는 이번 문장이나 저장된 사용자 진술에 실제로 있어야 하며 숫자와 단위도 일치해야 한다. 과거 진술은 더 최신 값이나 직접 입력을 덮어쓰지 못한다. 질문 문구는 바꿀 수 있지만 target·condition·입력 선택지와 계산값은 모델이 변경하지 않는다. 점수·해당 여부·조사자 결론은 AI 출력 대상이 아니다.

## 중복 제거와 의미

- 이미 사용 가능한 필드는 다시 묻지 않는다. 질문 카드 일부만 채워져도 필드별로 제외한다.
- USER가 모름으로 답한 항목도 자동 반복하지 않는다. 결과에는 입력 필요를 유지한다. 수정은 정보 요약에서 가능하다.
- 다른 무게·작업 조건은 서로 다른 condition/row_id로 유지한다. 최대 중량에 전체 횟수를 붙이지 않는다.
- 일반 작업의 무게를 사진 속 하중으로 복사하려면 같은 물건/무게라는 진술이나 추가 답변이 있어야 한다.
- 전체 하루 시간과 특정 동작 노출시간을 구별한다. 사진 비율로 노출량을 만들지 않는다.
- 말하지 않은 작업 특징은 UNKNOWN이다. 같은 작업에도 여러 부담 특성이 겹치므로 ‘다른 작업 없음’을 다른 특성의 NO로 확대하지 않는다. 화면에 열거한 미확인 특징을 ‘아래 특징은 모두 없음’으로 직접 선택했을 때만 묶어 NO로 기록한다. 이 묶음 선택은 AI 쓰기 대상에서 제외하며 결과 진행을 막지 않는다. 이 답변을 조건 행 전체를 기록했다는 답으로 쓰지 않는다. 행 전체 여부는 별도 `complete.<gate>` 항목이다.
- 같은 사진의 반대쪽 팔이나 다른 사진의 관찰을 현재 대표 사진의 사실로 복사하지 않는다. 현재 빠른 계산의 대표 사진은 계약의 방향 순서에서 먼저 등록된 사진이며, 다른 사진·행의 상세 계산은 고급 편집에서 조정한다.

## 저장·재실행

기존 `TASK.input_json.conditions`의 선택 키에 세션을 보관한다. 실제 값은 기존 conditions/legal/capture/manual에도 저장하므로 결과·Excel·고급 편집이 같은 값을 사용한다. 물리 여섯 테이블, 기존 분석/출력 snapshot, 이전 자료는 유지한다. 값이 없는 이전 자료는 기존 계약대로 읽는다.

일반 단일 선택은 즉시 저장하고, 좌우 짝 질문은 양쪽 선택을 모아 한 번 저장한다. 관련 항목 그룹은 하나 이상 선택하면 선택한 항목만 모아 저장한다. 숫자·텍스트 칸은 입력 중 짧은 지연 후 또는 필드를 떠날 때 저장한다. 결과 생성 전에 저장 요청을 기다린다. AI 네트워크 대기 중에는 DB 트랜잭션을 잡지 않는다. 입력 revision이 바뀐 뒤 도착한 AI 응답은 최신 사용자 값을 덮어쓰지 않는다. 삭제한 작업을 복원하지 않는다.

기본 화면에는 항목별 빈 입력칸이나 전체 질문 목록을 노출하지 않는다. 자동 정리 직후 대화 팝업이 열리고 답변 저장 후 다음 누락 질문을 고른다. 선택값만 보낸 회차는 로컬에서 계획하고 자유문장 추출과 빈 재시도는 AI를 사용한다. 자유문장 경로에서 추출 전 누락 목록으로 만든 질문이 답변 반영 후 이미 해결됐다면, 추출값을 먼저 저장한 뒤 갱신된 누락만 AI에 다시 보내 질문을 만든다. 선택형 질문에 유효한 선택지가 있으면 선택지와 ‘모르겠어요’만 기본 표시하고 답변창·답변 보내기는 렌더링하지 않는다. ‘직접 설명하기’를 누르면 보조 버튼을 답변창으로 바꾸며 같은 질문의 문장 초안을 유지한다. 선택형 작성 중 ‘모르겠어요’는 선택지에만 두고 숫자·텍스트 질문에서는 답변창과 함께 제공한다. 답변이 정상 처리되어 다음 선택형 질문으로 넘어가면 작성 영역을 다시 접는다. 초기 작업 설명이나 답변이 AI 실패로 미처리 문장 초안으로 남으면 질문이 달라져도 작성란을 열어 유지한다. AI 오류의 재시도 버튼은 접힌 작성 영역 밖에 표시하므로 글을 쓰지 않고도 다시 연결할 수 있다. 직접 값 수정은 요약의 ‘수정’을 명시적으로 선택할 때만 제공한다. 팝업은 Esc/닫기/나중에 확인이 가능하며 현재 정보로 결과를 볼 수 있다. AI 실패 시 응답 실패와 재연결을 표시하고 답변 문장을 보존한다. 문장 없이 재시도해도 마지막 저장 진술을 AI 문맥에서 버리지 않는다.

사진/모델 변경 시 영향을 받는 사진 추정만 재평가하며 작업 전체의 시간·횟수는 유지한다. 고급 편집에서 바뀐 실제 값은 세션보다 우선한다. 세션 이력은 작업 입력 변경으로서 snapshot에 보존하지만 전후 비교의 작업 조건 변화 목록에는 보조 세션 메타데이터를 펼쳐 쓰지 않는다.

기존 `quick_preview`와 `quick_interpret`는 호환 호출로 남는다. 새 간편 흐름은 위 세 서비스와 모듈을 사용한다. 과거 localStorage 초안은 호환 경로로 열 수 있으며 새 자동 저장 값의 정본은 SQLite다.

## 공통 AI 설정

`ergo/ai_config.py`는 공급자 클라이언트·DB와 독립적인 설정 계약이다. get_settings의 gpt_contract.fields/defaults가 두 설정 화면과 모든 AI 요청에 공통으로 쓰인다. 입력 정리·후속 질문·설명/기존 한 줄 입력에 별도 모델·시간·토큰 상수를 두지 않는다. `LOCO_AI_MODEL`, `LOCO_AI_REASONING_EFFORT`, `LOCO_AI_TIMEOUT_SECONDS`, `LOCO_AI_MAX_OUTPUT_TOKENS`가 초기값을 지정하며 APP_SETTINGS JSON의 명시값이 우선한다. 현재 기본 조합은 `gpt-6-luna` / `xhigh`다. 추론 미지원 모델은 추론 강도를 빈 값(전송 안 함)으로 설정할 수 있고 자동 모델 대체는 하지 않는다. 키는 기존 OPENAI_API_KEY 환경에서만 읽는다. 설정 변경은 이전 연결 상태를 미요청으로 바꾸며 다음 요청의 실제 응답이 와야 내부 연결 성공 상태를 갱신한다.

추가 확인 팝업에는 가로 진행 막대·퍼센트·확인한/전체/남은 항목 수를 함께 표시한다. 답변에 따라 항목 수가 달라질 수 있음을 안내하고, 이전 서비스처럼 progress가 없거나 잘못된 응답에서는 임의 퍼센트를 만들지 않고 확인 가능한 남은 항목 수만 보여 준다. 제목·하단 이동 버튼과 스크롤 본문을 분리하고, 답변창은 글자 16px·최소 높이 120px로 표시한다.

## 좌우 함께 확인 (2026-10-23)

좌우 짝 질문은 한 화면에서 왼쪽·오른쪽을 각각 선택한다. 각 쪽에 ‘모르겠어요’를 제공하고 양쪽에 응답한 뒤 ‘선택한 답변 저장’으로 기존 `intake_turn.answers`에 두 항목을 한 번 보낸다. 미선택 쪽을 0·NO나 반대쪽 값으로 채우지 않는다. ‘직접 설명하기’는 계속 사용할 수 있다. 이미 알려진 쪽이나 USER 모름은 짝 질문에서 제외하고 남은 쪽만 묻는다. 진행률은 묶음 화면 수가 아닌 원래 확인 필드 수를 유지하며 저장·revision·기존 snapshot 의미를 바꾸지 않는다.

## 관련 항목 묶음과 처리 중 안내 (2026-10-23)

현재 미확인인 몸통·목 최대 6개, 다리 3개, 움직임·힘 4개, 양팔·손목의 추가 자세 8개, 작업 특징 최대 9개를 관련 묶음으로 표시한다. 각 행에 항목과 선택 상자를 두고 ‘선택 안 함’과 명시적 ‘모름’을 구분한다. 하나 이상 선택하면 선택한 답변만 한 요청으로 저장하며, 남겨 둔 항목을 NO·0으로 만들지 않는다. KNOWN·USER 모름은 재질문하지 않는다. 단일/좌우 짝 질문과 직접 설명은 계속 제공한다.

진행률은 질문 화면 수가 아닌 확인 필드 수다. 예를 들어 남은 항목 40개가 보여도 40번의 팝업 응답을 뜻하지 않으며 한 묶음에서 여러 필드를 처리할 수 있다. 사용자 미처리 문장 초안은 선택값의 로컬 저장으로 처리 완료·삭제하지 않고 보존한다.

팝업과 일반 페이지에서 처리 중에는 작업 문구·회전 표시·왕복하는 막대·실제 경과 초를 보여 준다. 15초와 45초 이후 대기 안내를 바꾸고 매초 경과 숫자만 갱신한다. 이 막대는 처리 중 표시이며 완료 퍼센트나 남은 시간 추정이 아니다. 움직임 줄이기 설정에서는 회전과 막대 이동을 멈추고 경과 시간은 유지한다. 제목·하단 버튼과 본문 스크롤 구조, 모델·추론 강도·연결 성공 상태 비노출을 유지한다.


## 간단 확인 후 결과 우선 (2026-10-23)

간편 확인은 전체 계산 필드를 끝까지 소진하도록 자동 연속 질문하지 않는다. policy.quick_review_interval=5를 기준으로 사용자 확인 필드 수 또는 저장 회차 수 중 큰 값이 기준에 도달하면 다음 질문 대신 결과 우선 안내를 보여 준다. 기존에 많은 답변을 저장한 작업에도 적용한다. 이는 계산 완성 판정이 아닌 화면 진행 정책이며 미확인 사실·후보·실제 진행률·complete 값은 바꾸지 않는다. 사용자가 ‘상세 항목 더 확인’을 선택하면 현재 기록 수에서 다음 5개 단위 동안 확인을 이어갈 수 있고, 결과 화면에서 추가 확인을 여는 것도 명시적 선택으로 처리한다. 미전송 문장이나 저장 오류가 있을 때는 이 안내로 초안을 가리지 않는다.

단일 숫자 질문에서 단위가 일치하는 단순 숫자 응답(예: 회/시간 질문에 ‘2번’)은 기존 직접 answers 경로로 즉시 저장한다. 하루·시간당 등의 추가 문맥이나 단위 변환이 필요한 문장은 기존 AI 추출 경로를 유지한다. 0은 실제 0이며 미응답을 0으로 채우지 않는다.


## 기본 간편 입력: 묶음 서식 (2026-10-23)

새 서비스 응답의 `form_fields`가 있으면 간단 확인 횟수 제한/개별 질문 대신 작업 특징 → 작업 조건 → 결과의 고정 이동을 사용한다. 첫 화면에 작업 특징을 함께 표시하고 저장 후 해당 작업의 관련 조건을 선택·숫자 서식으로 묶어 표시한다. 관련된 KNOWN 값은 미리 표시하며 변경한 값만 기존 intake_turn.answers로 저장한다. 조건별 identity를 유지하고 서로 다른 중량·횟수를 합치지 않는다. 선택 보완인 사진 자세는 접을 수 있다. 미선택은 NO/0으로 자동 채우지 않으며 미확인 상태로 결과를 생성할 수 있다. 화면 단계 표시는 계산 완성률을 뜻하지 않는다. 결과 이동 후 개별 누락 질문을 자동으로 이어가지 않는다. 추가 설명은 선택 영역에서 AI로 정리할 수 있고 서식 선택·숫자 저장에는 AI 요청을 하지 않는다. 기존 응답의 questions/progress/complete는 호환·실제 계산 상태로 유지한다. form_fields가 없는 과거 초안은 기존 질문 화면으로 읽는다.

## 작업별 시간 합산 근거 (2026-10-22)

`fields[].derivations`는 숫자 근거 검증에서 허용하는 연산의 목록이다. 하루 총시간에만 `SUM_STATED_DURATIONS`를 허용한다. AI가 하루 일정으로 나열한 서로 다른 작업별 시간을 선택하고, 검증기는 원문·단위 변환·피연산자·합계를 독립 확인한다. `하고` 같은 특정 연결어는 필수 조건이 아니다. `및`·문장 나열·“총 작업은…”도 같은 근거를 표현할 수 있다. 예를 들어 “손을 높이 드는 걸 한 2시간 하고 키보드 작업 6시간 해”는 각 노출 120/360분을 유지하고 전체를 480분으로 기록한다. 원문에 “8시간”이 따로 없다는 이유로 버리지 않는다.

AI 응답의 하루 총시간은 `calculation:null|{operation,terms:[{quote,minutes},...]}`을 포함한다(2026-10-23). 합산에는 허용 연산과 원문 순서의 서로 다른 작업시간을 넣고, 단일 수치·모름에는 null을 넣는다. 이 응답 schema는 `fields[].derivations`에서 생성하며 다른 필드에는 계산 객체를 허용하지 않는다. 피연산자 수 제한은 `grounding.MAX_DURATION_TERMS`, 단위와 수사 처리는 같은 모듈의 공통 변수다. 모델 ID·추론 강도는 기존 AI 공통 설정을 따른다.

각 term의 인용은 전체 quote와 실제 사용자 원문 안에 있어야 하며 같은 원문 위치를 두 번 사용할 수 없다. `1시간 30분`·`한 시간 삼십분`은 90분인 한 수량이며 1시간/30분을 각각 독립 작업으로 떼지 않는다. `2시간(120분)`을 통째로 인용해도 두 단위가 같음을 확인한 뒤 한 번만 센다. 불일치 환산·잘못된 합계·총합 수치를 다시 피연산자로 사용한 중복은 거부한다. 과거 계산 객체 없는 응답의 단순 시간 나열도 읽되, 괄호 환산·별도 총합이 섞인 복잡한 인용은 구조화한 피연산자가 필요하다.

저장된 fact의 선택 `calculation={operation,unit,terms:[{minutes,quote}],value}`는 검증기가 정규화한 근거다. 복합 단위 하나를 분으로 변환한 근거의 operation은 `NORMALIZE_STATED_DURATION`이다. 이 값은 기존 conditions.daily_work_min으로 투영되어 결과/Excel이 같은 값을 쓴다. 다른 노출 필드도 복합 시간 단위는 읽지만, 여러 작업 노출을 더해 총시간으로 만드는 합산 권한은 없다. 사진/노출 행을 임의로 더하지 않는다. 겹침·포함·동시 작업·휴식·범위·다른 주기·부분 일정은 단순 합산에서 제외한다. 특정 동작의 범위 시간이 별도로 있어도 원문에 직접 명시한 확정 총시간은 그 범위와 구분해 읽는다. USER 직접 값·모름 우선권과 과거 분석 snapshot 불변성은 유지한다. 이 절의 과거 검증은 AUD-04에 해당한다. 다른 7건의 후속 정정 계약은 아래 저장 보완을 따른다.

## 최신 main 통합과 재질문 방지 (2026-10-23)

최신 main의 Excel 출력·사진 크롭·공통 이동과 2단계 묶음 확인을 기준으로 MediaPipe 및 저장 보완만 추가한다. 이미 KNOWN인 값과 USER가 모름으로 확인한 항목은 새 질문/질문 묶음에 넣지 않는다. 간편 묶음 서식에서도 기본 추가 입력에서 제외하고 닫힌 ‘이미 확인한 정보 · 수정하기’에서만 수정한다. 조건별 행과 좌우 사진의 identity를 유지하며 한 조건의 답을 다른 조건에 복사하지 않는다. ESTIMATED·CONFLICT 및 새 사진에 연결되지 않은 정보는 확인할 수 있다.

사진과 같은 물건이라고 확인한 유일 중량은 photo_load의 공통 해석으로 계산과 질문에 함께 사용한다. 이 파생값을 새 사실로 저장하거나 조회 revision을 올리지 않는다. 여러 중량, 확인하지 않은 연결, 명시적인 모름·무하중·직접 중량은 구분한다. 자동 저장과 수동 임시 저장이 같은 작업/생성시각을 가리키면 홈의 이어서 하기 카드는 수동 저장 하나로 표시한다. 별도 작업 초안은 보존한다.

사용자에게 보이는 시스템 용어는 frontend/user-language.json을 공통 사전으로 사용한다. 화면의 AI 본문·처리 상태·계산 근거 및 Excel 설명은 같은 뜻의 한국어로 표시한다. 과거 저장된 원문·직접 입력 근거·계산 코드·수치·단위·snapshot은 바꾸지 않는다. 새 AI 설명 지침에도 같은 사전을 제공하며 근거 참조 코드는 유지한다. 묶음 입력에서 미전송한 추가 설명은 다음 단계 저장과 함께 처리하고, 입력 단계와 수정 중 선택값은 초안 복원 대상이다.

## 원문 문장 인용과 반 시간 경계 (2026-10-23)

`grounding.evidence_quote`는 공백 정규화 후 연속 원문 일치를 우선한다. 연속 일치가 아니면 `EVIDENCE_POLICY`의 문장 경계(소수점 제외)로 나눈 둘 이상의 문장이 동일 메시지의 완전한 문장과 원래 순서·서로 다른 위치로 일치해야 한다. 마지막 미종결 문장은 실제 원문의 마지막 문장 전체와 같아야 한다. 단어 조합·부분 문장·의역·부정 삭제·역순·한 위치 재사용·여러 메시지 합성은 허용하지 않는다.

예를 들어 “드는 물건은 없어요. 사진은 한 사람의 전신이 나온 평소 작업 모습입니다. 손으로 밀거나 당기는 힘도 전혀 없어요.”에서 첫 문장과 마지막 문장을 붙여 인용한 `UNLOADED` 제안은 인정한다. fact.quote에는 중간 문장도 포함한 실제 연속 원문을 저장하고, requests.answers/decisions의 원본 인용은 바꾸지 않는다. `history.source_ids`도 같은 검증기를 사용하여 원래 메시지를 연결한다.

수치와 UNKNOWN의 검증은 모델이 실제로 인용한 문장으로 한다. 연속 근거 범위를 복원하면서 포함된 중간 문장의 다른 숫자나 모름 표현을 해당 제안의 근거로 새로 허용하지 않는다. 현재/과거 원문 구분, USER 소유권, 늦은 응답 재조정, 사진 소유권, 기존 snapshot 불변성은 유지한다. 사진·작업 대상에 숫자를 의미적으로 배분한 결과 자체는 모델의 추출이며, 이 검증기는 모든 의미적 배분의 정확성을 일반 보증하지 않는다.

반 시간은 `HALF_QUALIFIERS/HALF_PARTICLES/HALF_ENDINGS`와 단어 끝 경계를 따른다. “한 시간 반이에요”, “한 시간 반 동안”, “1시간반씩”, “2시간반을”은 90/150분이며 “3시간 반복”, “3시간 반대”, “3시간 반드시”, “3시간 반품”, “3시간 반도체”는 180분이다. 원문 공백을 지우기 전에 수량을 읽고 위치만 공백 정규화하여 비교한다. 원문에 없는 반 시간을 더하거나 기존 복합 수량의 일부만 독립 수량으로 읽지 않는다.

회귀 근거는 `tests/test_intake_evidence.py`와 실제 Luna 응답을 기록한 `tests/fixtures/intake-recorded-grounding-20261023.json`이다. 재생 시험은 새 외부 호출이 아니며, 실제 서비스·격리 SQLite·재시작·분석 snapshot·Excel 셀의 저장 대조를 수행한다.

## 명시적 모름의 한국어 근거 (2026-10-23)

AI가 `text=UNKNOWN`을 제안하면 공통 `grounding.unknown_evidence`가 실제 인용의 명시적 모름 표현을 확인한다. `UNKNOWN_POLICY`에 서술 표현·국소 부정 경계를 둔다. “모르겠어요/모르겠습니다”, “모릅니다”, “몰라요”, “모름”, “알 수 없어요/알지 못합니다”, “미확인/미측정”, “확인 불가/확인할 수 없어요”, “기억이 안 나요”를 인식한다. “모르지 않아요”, “알 수 없는 건 아닙니다”, “미확인 항목은 없어요” 등 모름을 부정하는 표현과 무관한 긍정 사실은 모름 근거가 아니다. 일반적인 모든 한국어 의미 해석을 보증하는 문법기는 아니다.

인용 자체는 기존 evidence_quote로 원문 존재·문장 연결을 검증한다. 복원된 연속 근거의 중간 문장에만 모름 표현이 있어도 모델이 실제 인용하지 않았다면 UNKNOWN의 근거로 삼지 않는다. 유효한 명시적 모름은 기존 `value=null,state=UNKNOWN,source=USER,origin=AI`로 저장하여 같은 질문을 다시 하지 않는다. 모름 때문에 숫자 0/NO/무하중을 만들지 않는다. 최근 직접 값·더 최신 사실·사진 소유권과 지연 재조정 규칙을 바꾸지 않으며 늦게 왔다는 이유로 버리는 만료 조건을 추가하지 않는다.


## 추가 질문 최소화 (2026-10-23)

계산기가 이미 완료한 범위의 작업 특징은 후보와 묶음 서식 모두에서 제외한다. 원래 미확인 값을 NO로 저장하지 않는다. 작업 설명을 먼저 보이는 답변 칸에서 한 번에 정리하고, 개별 수정은 접힌 영역에서 제공한다. 화면에 열거된 남은 작업 특징은 사용자가 명시적으로 한 번 확인하여 NO로 저장할 수 있다. 먼저 작성 중 설명과 직접 선택을 저장하며 새로 알려진 YES, 이전 USER 모름, 이미 확인된 값은 일괄 확인으로 덮지 않는다.

공통 intake POLICY.optional_photo_destinations는 사진 점수를 더 보완할 때의 항목을 정의하고 form_prompt_limit은 한 자연어 안내에 나열할 항목 수를 정의한다. 사진의 미확정 보완 항목만 남으면 기본 팝업을 강제하지 않고, 사용자가 선택해 더 확인할 수 있다. 해당 값은 미확인으로 보존하고 REBA 미완성/현재 정보 출력의 기존 의미를 유지한다. 작업 정보가 충분하거나 사용자가 모른다고 확인한 뒤에는 빈 단계를 건너뛴다. 미전송 설명/직접 수정은 결과 이동 전에 저장한다.

회귀는 test_question_minimization.py와 frontend-question-minimization.cjs에서 계산 완료 시 9개→0개, 남은 특징 한 번 확인, USER 모름/직접 YES 보호, 미전송 설명 우선 처리와 실패 보존을 검사한다. 실제 질문 수는 저장 필드 수 또는 접힌 사진 보완 수와 구분하여 사용자 답변 동작으로 검증한다.

## 질문 전 원문 교차확인 (2026-10-23)

새 자연어를 저장한 회차는 질문을 보여 주기 전에 FOLLOWUP 원문 교차확인을 한 번 수행한다. 다른 유효 질문이 있어도 앞선 제안·거절사유·현재 사실·원문 당시 사진 범위를 대조하여 빠진 명시 사실을 추가한다. 조회/중복 읽기, 직접 선택 답변만의 저장, plan=false에는 추가 호출하지 않는다. 기존 원문 검증·USER 우선권·지연 재조정·불변 snapshot을 유지하며 만료 조건을 추가하지 않는다. 상세 계약은 [원문 교차확인](verification/2026-10-23-source-coverage.md)을 따른다.


## 사진별 관측값 소유권 (2026-10-23)

사진 자세 값은 같은 원본 사진·신체 부위에만 적용한다. `manual.<scope>.<field>@photo:<photo_id>`가 정식 식별자이며 `photo_id`, 사진 방향, 원래 각도·신뢰도·측정 정책·엔진 근거를 함께 보존한다. 대표가 아닌 사진에서 읽은 값도 저장하지만 대표 사진의 빈 자세를 대신 채우지 않는다. 같은 사진에서 이미 확인한 값과 직접 모름으로 남긴 값은 다시 묻지 않는다. 남은 질문·묶음 서식에는 ‘왼쪽에서 찍은 사진 · 오른팔’처럼 사진 방향과 신체 부위를 표시하고 내부 식별자는 노출하지 않는다.

기존 `@default` 자세 값은 당시 대표 사진에만 연결하는 호환 별칭이다. 이미 저장된 사진별 USER 값·모름을 옛 자동 추정 별칭으로 덮지 않는다. 사진 교체·삭제 시 다른 사진의 사용자 값과 원문·시각을 보존하고 제거된 사진 값은 현재 계산에 투영하지 않는다. 동일 원본·모델 설정·근거를 반복 조회하거나 재시작하면 저장 JSON·revision·근거 시각은 변하지 않는다.

정면·후면의 몸통·목 기울임과 팔 벌림 관측은 원래 사진·신체 좌우별로 보존한다. 한쪽 팔의 최대 각도를 양팔에 복사하지 않으며 확실한 양성 측정만 자동 변환한다. 낮은 신뢰도·점수 경계·손 가림·손바닥 방향 불명확은 확인 대상으로 남긴다. 참고용 목 각도와 추정 3D 좌표는 기존 REBA 확정값으로 승격하지 않는다. 하루 시간·하중 추정, 대표 사진 선택, 양팔 REBA 완성·최댓값 계산은 유지한다.

기존 여섯 테이블과 TaskInput 2.0을 유지한다. `TASK.conditions.intake_session`의 선택 `photo_observations`와 fact 소유권·근거 메타데이터로 저장하며 물리 migration은 없다. 분석·출력 snapshot은 불변이고 Excel 입력 근거는 각 행의 실제 사진 식별자로 조회한다. 같은 범주값인 두 사진도 각자의 각도·인용을 유지한다. 세부 계약과 검증 한계는 [사진별 검증](verification/2026-10-23-photo-ownership.md)을 따른다.

### 명시 총시간과 불필요 계산 메타데이터 (2026-10-23)

원문을 그대로 복사한 단일 확정 하루 총시간과 제안 수치의 단위 환산이 직접 일치하면, AI가 함께 붙인 불필요한 합산 메타데이터 때문에 그 값을 거절하지 않는다. `grounding.DIRECT_TOTAL_POLICY`가 이 우선순위와 부정·불확실 경계를 관리한다. 예: “하루 전체 실제 작업시간은 5시간입니다”의 300분은 직접 저장하며, 별도 작업 피연산자가 인용에 없다는 이유로 재질문하지 않는다. 원 AI 제안의 calculation과 결정·원문 연결은 이력에 그대로 보존하고, fact에는 검증하지 않은 합산 근거를 저장하지 않는다. 틀린 총값·단위·잘린 복합 시간·범위·부정·불확실 총시간은 이 우선 규칙으로 허용하지 않는다. 단일 명시 총시간이 없는 합산은 기존 원문 피연산자·단위·순서·중복·산술 검증을 계속 거친다. DB 스키마·기존 snapshot·USER 우선권은 바꾸지 않는다.

### 실제 사진의 AI 관찰 (2026-10-23)

사용자가 사진 분석을 요청하는 기존 intake_turn 계획 실행에서 등록된 현재 크롭 사진을 실제 Luna 이미지 입력으로 보낸다. 계약은 `ergo.vision.contract`, 서비스는 `service.photo_vision`이며 모델·추론 설정은 기존 ai_config를 공유한다. 사진별 동작·몸통·목·무릎·좌우 팔·좌우 손목·잡은 모습 9개 관찰과 보이지 않거나 모호한 이유를 보존한다. MediaPipe의 수치 각도와 구분한다. `conditions.intake_session.photo_vision` 및 동일 응답 경로에 사진별 원본/전송 JPEG SHA, task/photo 소유권, signature, raw_response, 연결·진단을 저장하고 base64/EXIF를 DB에 넣지 않는다. 여섯 테이블과 과거 snapshot은 유지한다.

등록 이미지/view/소유권·모델/추론/프롬프트·이미지 정책으로 캐시하며 읽기·재시작·직접 선택 답변·plan=false에는 이미지 API를 호출하지 않는다. 변경된 사진의 최초 요청은 사진별 병렬 실행하며 지연 응답을 시간으로 폐기하지 않는다. 다른 사진이나 삭제·교체된 작업에 이전 결과를 적용하지 않는다. 불확실/안 보임은 NO가 아니다. 허용된 분명한 boolean 자세와 4개 작업 특징의 YES만 별도 검증 경로로 source=VISION에 반영할 수 있다. USER(직접 모름 포함), 텍스트 AI, SAVED, 유효한 POSE를 우선한다. 사진에서 무게·힘·시간·횟수·정밀 각도·법정/의학 판정을 만들지 않는다. 상세는 [photo-vision.md](photo-vision.md)를 따른다.

### 사진 등록 세대와 사용자 사진 상황 우선권 (2026-10-23)

`photo_identity.REGISTRATION_KEY`는 새 PHOTO.metadata_json 행에 UUID를 부여하며 update로 교체하지 않는다. 물리 스키마는 유지한다. legacy 행은 경로/소유 ID로 결정되는 토큰을 읽고 조회 중 metadata를 쓰지 않는다. 사진 signature는 [view,photo_id,원본SHA,등록세대]이며 과거 triple을 호환한다. 같은 SQLite ID·파일경로·바이트·view로 재등록해도 이전 이미지 및 텍스트 사진 응답이 새 등록에 적용되지 않는다.

사용자가 context=NO로 사진 상황을 부정하면 raw 관찰과 캐시는 보존하되 VISION 소유 manual/작업특징 입력은 UNKNOWN으로 돌려 실제 투영값도 해제한다. USER·텍스트 AI·SAVED·POSE 소유 값은 건드리지 않는다. context=YES로 직접 정정하면 같은 이미지 관찰을 재사용하며 추가 이미지 API를 호출하지 않는다. 같은 turn의 텍스트 추출 뒤 저장에도 이 우선권을 적용한다.
