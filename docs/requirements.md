# 요구사항

> 문서 ID ERGO-REQ-001 · 설계 버전 1.4 · 기준일 2026-10-14 · 데모 개발 기준

## 1. 목표와 범위

Windows용 Electron 데스크톱 데모에서 조사자가 **한 사람이 바닥 상자를 바로 앞 선반에 올리는 작업**을 기록한다. 화면은 Electron, 분석·저장·Excel은 로컬 Python 서비스가 담당한다. 앱이 사진별 자세·REBA와 고용노동부 고시 제2020-12호 제3조 11개 기준 초안을 계산하고, 조사자가 결과를 검토해 Excel로 내보낸다.

지원 작업은 `FLOOR_TO_SHELF_BOX_SINGLE_PERSON` 하나다. 여러 작업을 등록할 수 있으나 모두 같은 종류다. 한 작업은 같은 작업자·상자 중량·선반 높이·방법을 사용한다. 걷기·몸 돌리기·공동 들기·다른 물체 작업은 데모 분석 범위에 포함하지 않는다. 작업자 수는1이며 중량을 인원으로 나누지 않는다. 조건이 다르면 별도 작업이다.

이번 단계는 **데모 기능 구현**이다. 테스트 추가/실행, 보안·암호화·권한, 승인 게이트, 운영 차단장치, DB 차단 제약/트리거를 요구하지 않는다. 이런 기능은 구현 이후에 검토한다. 문서 정합성은 문서 전체를 읽고 수동 대조한다.

## 2. 입력·계산 원칙

- `BOX_LIFT_15_V1`: 정상 작업3회 × 지정 순간5개 =15슬롯. 사진 다중 업로드 후 조사자가 회차·순간을 배정한다.
- 순서는 CYCLE_START → LIFT_OFF → MID_LIFT → SHELF_APPROACH → CYCLE_END. 정확한 촬영 기준은 [기능정의서 §2](기능정의서.md#2-촬영-프로토콜)에 있다.
- 10분 관찰/일정 간격 촬영을 요구하지 않는다. 사진 비율·촬영3회를 하루 노출시간·하루 횟수로 환산하지 않는다.
- 시작·종료의 하중은0, 들기3순간의 하중은 상자 전체 중량이다. 지지 상태를 모르면 사진 점수는 미완전으로 표시한다.
- MoveNet Lightning은17관절 추출용이다. 상자·손가락·발끝·접촉·비틀림을 자동 인식했다고 표시하지 않는다.
- REBA와 고시 기준은 각각 독립 계산 모듈이다. GPT에15장을 보내지 않으며 수치 요약으로 설명 문장만 제안한다.
- 값이 없으면 null/UNKNOWN과 필요 항목을 표시한다. 가짜0·정상 자세·비해당으로 채우지 않는다.
- 15슬롯 미완성, 수동 입력 누락, 분석 실패는 결과에 표시한다. 분석·저장·검토·초안 내보내기를 일괄 차단하지 않는다.
- 입력 버전과 분석 스냅샷으로 현재/과거 결과를 구분한다. 동시 수정 잠금이나 예상 버전 가드는 넣지 않는다.

## 4. 유지보수와 모듈화

DB는 SURVEY/TASK/PHOTO/ANALYSIS/APP_SETTINGS/EXPORT_LOG의6개 테이블이다. 상세 입력·15슬롯·관찰·15사진 결과·11기준 결과는 명시된 DTO의 JSON으로 저장한다. 범용 EAV·별도 revision 테이블·판정 trigger·복잡한 FK 구조를 만들지 않는다.

호출 흐름은 Electron renderer(UI)→preload→main→로컬 Python Application Service다. main이 Python 자식 프로세스 하나를 실행하고 stdin/stdout의 UTF-8 JSON Lines로 기존 서비스 API를 전달한다. Electron IPC와 이 메시지 연결은 호출 전달만 담당한다. HTTP 서버·포트 설정·인증/승인 절차를 추가하지 않는다. Electron이 DB나 점수표를 따로 구현하지 않으며 Python storage가 기존 SQLite를 관리한다.

사진은 Electron의 다중 파일 선택/끌어놓기로 얻은 절대경로를 import_photos에 전달한다. 원본은 사용자 위치에 유지한다. EXIF 방향을 적용한 미리보기는 Python capture의 get_photo_preview가 반환하며 화면에서 사용한다. Excel 저장 경로도 Electron 파일 선택창에서 정해 Python report에 전달한다.

각 계산 모듈은 입력 DTO→출력 DTO로 동작하며 다른 모듈의 DB/내부 함수를 직접 호출하지 않는다. 분석은 백그라운드에서 처리하고 기존 RunHandle/get_analysis/cancel_analysis로 진행/취소를 제공한다. 사진을 다시 추론하지 않고 REBA/고시만 재계산할 수 있어야 한다. 모듈별 경계는 [API 계약서](API_계약서.md), 저장 방식은 [DB 아키텍처](DB아키텍처_설계서.md)에 있다.

## 5. 결과 표현

15장은 제품 입력 기준이며 법정 표본 수·통계적 대표성을 뜻하지 않는다. 사진에서 얻은 각도는 측정 후보이며 REBA에 필요한 수동 범주는 조사자가 확인한다. 누락 REBA 총점은 null, 부분 표본 최대와15장 전체 최대는 구분한다.

자동 후보는 몸통/좌우 위팔·아래팔/무릎의6개 자리로 반환하며 제안값·근거각도·confidence·검토사유를 표시한다. 후보 적용은 기존 사진별 ManualValue로 저장한다. 선택 사진에 공통 관찰값 적용, 같은 순간의3회차 편집, 개별 사진 수정을 제공한다. 자동 일괄 적용은 각 사진 자신의 후보를 쓰며, 직접 관찰 복사는 사용자가 고른 필드/대상에만 적용한다. 목은 중립/0..20° 굴곡1, >20° 굴곡/신전2, 관찰불가null로 수동 선택한다.

11개 기준의 초안은 확인된 제외→해당 기준 모순→확실한 미달→결론에 필요한 누락→미결정 해석→해당 순서로 정한다. 결론을 바꾸지 않는 제외기간/일일시간 누락을 모든 기준의 필수 입력으로 만들지 않는다. 초안과 조사자 결론은 별도로 보존한다. GPT 요약에도 초안/조사자/effective 상태와 출처, 제외/누락/검토사유, REBA 미계산/미완전/완전을 전달한다. 미계산과 계산한0을 구별한다.

‘조사자 검토 완료’는 사용자가 누른 검토 표시다. 계산 완전성과 별도로 표시하며 미완전 상태에서도 사용할 수 있다. 이를 법적 승인이나 모든 입력이 채워졌다는 뜻으로 사용하지 않는다. 고시 공식 해설의 미확인 해석, 실제 사진 정확도, 운영·보안 요구는 구현 이후 별도 검토 항목이다.

출력의 검토 여부는 선택 analysis_id가 검토ID목록에 있는지로 정하고 검토 현재성은 조사 metadata_revision/분석CURRENT까지 비교한다. 포즈·REBA·고시의 계산 부족은 검토와 별도다. UI/Excel/ExportReceipt는 report가 만든 같은 상태를 사용하며 대표사진 포함 옵션은 ExportSnapshot에 저장한다. Electron 실행 구조를 반영한 문서 버전은1.4, 기존 계산 DTO/보고서 버전은1.3, REBA 규칙은 REBA_TABLE_2000_V2다. 호출 연결/미리보기용 데이터는 계산 snapshot/DB에 새 컬럼으로 저장하지 않는다.

Excel 요약은 조사 정보→작업 결과→입력 부족/검토 필요 항목→해석 안내 순서다. 계산 입력 부족 기준 수와 추가 검토 기준 수는 각각11개 기준 단위, REBA 미완료 사진 수는15슬롯 단위로 집계한다. 조사자 결론과 검토 표시가 계산의 부족 항목을 지우지 않는다. 미분석/미계산은0건으로 채우지 않는다.

SUMMARY 작업표는14열이며 정확한 순서는 API §7에 있다. 조사정보는 위 개요, input_revision/규칙은 TASK_INPUTS, 대표슬롯은 PHOTO_REBA 상세블록, 진단/적용 설명은 아래 작업ID·분석ID가 붙은 영역, 고정 안내는 아래 안내영역에 둔다. 정보는 보존하고 작업표의 폭을 줄인다. 시트는 기존 네 개를 유지한다.

다음 입력 안내는 기존 결과 유무/상태/저장된 포즈 진단/누락 필드/검토 사유에서 회차·촬영 순간·좌우·기준 번호와 항목 이름을 붙여 만든다. report가 next_inputs[].message로 구성해 UI와 Excel에 같은 문구를 제공한다. has_incomplete는 원래 결과에서 직접 산출하며 별도 미완전 사유 분류/배열을 요구하지 않는다. 이 값은 저장·분석·검토·출력 허가 조건이 아니다. 대표사진 옆에 REBA 구성점수를 표시하고, 기준별 비교 근거는 모든 항목을 표시한다. 제목/본문 글꼴·상태 글자와 색·필터·틀 고정·줄바꿈과 출력 시각/버전/식별자를 문서에 정한다. 집계와 안내는 report의 파생값이며 별도 DB 테이블이나 완료 차단을 요구하지 않는다.

현재 `ergo/`·구 SQL·구 시험은 이전 프로토타입이다. 문서의 새 데모가 구현되었다는 증거가 아니다. 이번 작업은 필수 문서를 docs에서 직접 관리하는 것이다.

유서하는 한정욱이 제공하는 storage를 호출하고 김나리는 기존 서비스 API를 화면에 연결한다. 한정욱은 DB 구현 후 데이터 연결·통합 문제 해결을 지원한다. 백엔드에 계산·API·출력이 집중되므로 각 반복에서 동작하는 부분을 먼저 연결하고 남은 작업을 재배정한다.

DB는 SURVEY/TASK/PHOTO/ANALYSIS/APP_SETTINGS/EXPORT_LOG의 6개 테이블과 JSON을 유지한다. 테스트 추가/실행, 가드, 보안·운영 차단장치, 복잡한 DB 제약, 설치 프로그램 제작은 이번 범위에 추가하지 않는다.

### 7.3 애자일 진행 방식

1. 한정욱이 아래 백로그의 우선순위와 진행 상태를 취합한다. 각 항목은 할 일·진행 중·앱에 연결됨으로 공유하고, 연결되지 않은 개별 함수는 실제 기능과 구별해 기록한다.
2. 목요일 09:30에 첫 작업을 배정하고 금요일 09:00에 남은 작업을 조정한다. 시작 공유는 10분 안에 현재 작업·막힌 지점·다음 연결 항목을 정리한다.
3. 2–3시간 단위로 구현하고 표에 정한 시각에 같은 Electron 앱에서 연결된 기능을 짧게 보여준다. 사진 등록·분석·점수·저장·Excel 중 해당 반복에서 추가된 흐름을 실제 자료로 실행한다.
4. 반복 끝에 남은 문제와 다음 작업을 조정한다. 문서에 없는 계산 규칙을 담당자가 임의로 만들지 않고 기능정의서/API의 해당 부분을 함께 고친다.
5. 한정욱이 금요일 데모까지의 작업 순서를 조율한다. 변경 요청이 생기면 추가 작업과 밀리는 작업을 백로그에 함께 반영한다.

이 진행 방식은 팀의 작업 관리다. 앱의 분석·저장·검토·출력에 승인 절차나 완료 차단을 추가하지 않는다.

### 7.6 연결 계약과 모듈 경계

- 김나리의 Electron main이 Python 자식 프로세스를 실행하고 preload의 기존 호출을 UTF-8 JSON Lines로 전달한다. 유서하의 Python 서비스가 같은 request_id로 Result를 응답한다.
- 서비스명·params·DTO·오류는 API 계약서를 따른다. 공용 필드 변경은 유서하가 호출 측과 한정욱의 저장 매핑까지 공유하고 한정욱이 문서 정합성을 취합한다.
- 유서하의 계산 모듈은 입력 DTO를 받아 출력 DTO를 반환한다. 저장은 한정욱의 storage가 맡고, 화면은 반환된 점수·판정을 표시한다.
- 원본 사진 경로, EXIF 적용 후 좌표, 선택 analysis_id와 snapshot을 화면·DB·Excel에서 동일하게 사용한다.
- docs/ui SVG는 화면 제작 참고 자료이며 필드·동작·문구는 최신 화면설계서/API를 기준으로 구현한다.
